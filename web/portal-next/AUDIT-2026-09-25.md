## 2. Bugs found

### B1. Brand → client impersonation sends the wrong field. **[verified against spec]**
`HttpClient.exchangeToken()` always sends the id as `brandId` (`packages/core/src/api/http.ts:294-295`). What each spec expects on `POST /token/exchange`:
- brand API: `token, username, brandId`
- client API: `token, username, clientId`
- user API: `token, username`

A brand admin dropping into a company would send `brandId` to the client API. The one test (`http.test.ts:230`) never passes an id, so it doesn't catch this.
**Fix:** take the id field name as a parameter, or choose it from the target API.

### B2. A 5xx during token refresh logs the user out. **[verified by reading code]**
In `refreshOnce()`, any `ApiError`, including 502 and 503, returns `null`. `raw()` then clears the tokens and calls `onSessionExpired`. The comment says the opposite ("a network blip should not destroy the session"). Both `catch` branches are also redundant.
**Fix:** return `null` only for 400/401. Rethrow everything else.

### B3. Unlisted writable fields are dropped from every PUT. **[code verified; backend effect inferred]**
`buildSubmitPayload` only walks the fields laid out in `descriptor.sections`, and `EntityForm` only seeds those fields from the loaded item. The README's own API rule says "a field left out of the payload is cleared". Together, that means editing a record wipes every writable field the descriptor doesn't list.
- In the user app it happens to be harmless: `CallForwardSetting.user` is omitted, and the `/my` endpoint presumably pins it.
- In the client, brand and platform apps it's a data-loss bug waiting to happen. `Ddi`, `User` and `Company` have dozens of writable fields.

**Fix:** seed from the full fetched item and send every writable field in the write schema. Fields the form doesn't show pass through unchanged, and fields hidden by a toggle still become `null`.
**Before building more:** confirm the "omitted = cleared" behaviour on a real backend, then add a test.

### B4. Relation dropdowns silently stop at 500 rows. **[verified]**
`useRelationOptions` requests `itemsPerPage: 500` and ignores `X-Total-Pages`. A large company's extensions or DDIs will quietly be missing from the dropdown. The old portal fetched 1000 rows, so it had the same problem at a higher limit.
**Fix:** use a searchable async combobox that runs a server-side `partial` filter.

### B5. Relation option cache key ignores `labelFrom`. **[verified]**
The query key is `[app, resource, 'options', filterBy]`. If two relations point at the same resource with different `labelFrom`, they share a cache entry, and one of them shows the other's labels.

### B6. Mistranslation from keying by English text. **[verified]**
`FaxesInOut.dst` is labelled `'To'`, which takes the old portal's `es` translation "Hasta" ("until", from date ranges). Short keys like To, From and Type will collide like this.
**Fix:** use context keys (`'To_fax'`) or i18next `context` for short words.

### Minor
- **Search fires on every keystroke.** `EntityList` has no debounce, so each keypress sends one API request. [verified]
- **Two tabs can log each other out.** `TokenStore` reads storage only at construction and has no `storage` event listener. If refresh tokens rotate, a second tab of the same portal holds a stale refresh token and gets logged out. [code verified; rotation depends on deployment config]
- **Dead chart config.** `recharts` is a dependency and gets its own `manualChunks` rule, but nothing imports it. [verified]
- **Packaging needs a git checkout.** `debian/rules` runs `codegen:check`, which uses `git diff`. A build from a tarball without `.git` will fail that step. [inferred]

## 5. Recommended order

1. **Fix the core before adding apps.** Each fix is small, but every later app inherits it.
   - Fix B3: full-resource PUT. Validate on a real backend first.
   - Fix B1 (exchange field) and B2 (refresh error handling), with tests.
   - Render `rowActions` in `EntityList`. Add a generic `download` / `play` action that uses `HttpClient.download` and the binary operations the manifest already lists.
   - Add an async searchable relation picker (B4) and fix its cache key (B5).
   - Extend `extractKeys` to scan `packages/core`, and debounce search.
   - Add `@testing-library/dom` and at least one component test each for `EntityForm` and `EntityList`.
2. **Close the user-app parity gaps.** Voicemail playback, recording download, fax file and resend, voicemail settings, preferences, password, QR code. This is the first real use of row actions and custom screens, and it's small enough to finish.
3. **Descriptor codemod.** Converting the ~194 remaining old entity definitions by hand is the biggest single cost. A ts-morph script that pulls labels, enum options, visibility toggles and ACL idens from `web/portal/*/src/entities/*/` would pay for itself before the client app is half done.
4. **Client app.** Start with DDI, User, Extension, Terminal, Hunt group, IVR and Queue. Then the WebSocket active-calls feed and the channel-usage charts, which will be the first real use of `recharts`.
5. **Brand app, then platform.** Platform comes last because it's the smallest.
